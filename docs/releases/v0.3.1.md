# ACast v0.3.1 发版说明

## 更新亮点

### 彻底根除 ADisplay 电视投屏中断 (Playback Stopped) 与 AirPlay 400 异常

#### 1. 深入 ADisplay 源码剖析两大致命根因
* **根因 1：ADisplay 点播中转引擎误判实时直播流**
  * 在 ADisplay 源码 `MediaRelay.cpp` 与 `MediaSource.cpp` 中发现，只要 URL 包含 `.m3u8` 且分片是 `.ts`，ADisplay 就会误判为爱优腾等 APP 的点播片源（VOD），强行启用 `MediaRelay` 拦截并转封装为固定分片；
  * 该换封装逻辑专为静态 VOD 设计，在末尾强制注入 `#EXT-X-ENDLIST` 标签，导致大屏 AVPlayer 播完前 4 秒切片后判定流已结束，触发 `didPlayToEndTimeNotification` 并报 `Playback Stopped`；
* **根因 2：ADisplay 底层 AirPlay 硬编码限制**
  * 深入 ADisplay 引用的 UxPlay 库源码 `http_handlers.h` 查明，其 AirPlay 视频播放接口（`POST /play`）硬编码要求必须是 `application/x-apple-binary-plist`，并且必须包含 `clientProcName`（仅限 YouTube）和 `uuid`，因此遇到普通投屏的 `text/parameters` 或 `xml plist` 会直接抛出 `Play request Content is not binary_plist (unsupported)` 并返回 `400 Bad Request`。

#### 2. 针对性架构优化与彻底根治方案
* **直通原生流接口 `/live`（绕开有缺陷的点播换封装拦截）**：
  * 在 Android 发射端新增并首选 `/live` 直通端点（`http://<ip>:8088/live`）；
  * 由于 URL 不以 `.m3u8` 结尾，ADisplay 的 `looks_like_hls` 与 `is_relayable` 判定直接为 false，彻底阻止 ADisplay 介入错误换封装；
  * `LocalHttpTsServer` 响应头注入标准 `Content-Type: application/vnd.apple.mpegurl`，使 ADisplay 的底层系统级播放器（AVPlayer / ExoPlayer）直接以原生 Live HLS 直播模式顺畅接流，永无 `#EXT-X-ENDLIST` 限制，彻底告别 4 秒断流！
* **分片保底与防空切片机制**：
  * 在推流服务启动瞬间预注入合规待命分片，确保无论大屏何时连入拉取 M3U8 清单，列表内永远包含合法有效分片，彻底杜绝播放器因解析到空列表直接触发失败；
  * 动态降低分片切片门限（400ms / 100KB），大幅降低起播与推流延迟；
* **DLNA / AirPlay 通道智能引导**：
  * 针对 ADisplay 等复合设备，明确以标准稳定的 DLNA 协议作为主通道，保障音画流转 100% 稳定可靠。
